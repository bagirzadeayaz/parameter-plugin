# Kontakt product search

## Independent product searches

A newly submitted full product name or an explicit request to search again starts a fresh search, even when it exactly matches the immediately preceding product. Call `prepare_product_search` without `task_id` again, resolve any needed variants, and call `start_product_search` to create a new record. Do not answer by copying the earlier response, fetching an earlier saved result, reusing its PDF, or treating a matching product name as a cache hit. Perform new native Web Search after the new record starts, reopen supporting pages, inspect image pixels again, and generate the new record's PDF. Identical verified values are acceptable; skipped research is not.

Only explicit requests to view, download, discuss, or continue an existing result use that saved record. Short answers to pending variant questions and parameter-specific follow-ups retain the current search. If the user explicitly requests modifying or rerunning a particular saved record, retain the existing approval requirement; a new independent search must not overwrite that record.

Treat each new product search as an independent evidence task. Use the current product request, its confirmed variant choices and explicit applicable user constraints, the workflow returned for this request, and the task's returned schema. Do not carry over product facts, model or market assumptions, source claims, image observations, completion claims, or formatting examples from earlier searches or unrelated chat discussion. Prior URLs may be discovery leads only: reopen the relevant pages and inspect image pixels for this search before using them as evidence.

Preserve continuity within the same search: retain its product identity, user corrections, pending choices, confirmed selections, task ID, runtime ID, and evidence already verified for that search. A colour/storage answer, retry, or follow-up is not a new search. For questions about an existing saved result, retrieve that result and its recorded evidence rather than reconstructing it from chat memory; distinguish recorded evidence from newly verified facts. Do not rerun a saved search without the approval required below.

This is an evidence-scoping rule, not context deletion or a replacement for higher-priority instructions. It must not discard relevant user instructions, authorize extra actions, or claim that the chat context has been cleared.

## Non-terminating workflow contract

A product request is one transaction: **start → research → recover → validate → save → generate PDF → render**. This contract applies in every new chat and does not depend on earlier conversation context.

- Do not send a final response after `start_product_search`, during research, or after a failed `validate_product_search_draft` call.
- A validation error is a loop instruction, never a user-facing result. Execute the requested recovery in the same turn, rebuild the draft, and validate again.
- If fields are missing, finish the required dedicated searches for every missing field before validating again. Do not summarize the missing fields as the result.
- The only successful terminal state is a saved result with its generated PDF followed by the complete rendered output. A verified invalid or ambiguous product configuration is a pre-search pause: present interactive choices and wait for the customer to select one before starting a search. The other terminal states are unavailable public service access, unavailable native Web Search, cancellation, or a genuinely unrecoverable service failure.
- Never expose internal validator, schema, image-metadata, routing, or worker-state errors as the product-search answer.

## Customer-facing communication

Treat the conversation as a product-information service for a non-technical customer. Internal work may be complex, but the visible wording must stay simple and useful.

- Write every customer-facing message in Azerbaijani, even when the request or earlier chat is in another language. This includes the opening, progress, variant choices, questions, failure explanations, completed result, source summary, and PDF-facing prose. Keep product names, model codes, measurement units, website names, direct links, and verbatim source quotations as evidence requires. Do not translate or alter normalized parameter values.

- Never narrate chain-of-thought, LLM activity, tool orchestration, prompts, agents, workers, routing, schemas, validators, metadata repair, evidence recovery, query counts, source-by-source processing, or internal phase names.
- Do not publish a checklist or timeline of research stages. Do not say that pages are being extracted, evidence is being reconciled, validation is running, or a draft is being rebuilt.
- Before the final result, send at most one short opening message. If the search continues for more than about 60 seconds, an occasional progress update is allowed only when the indicative percentage changes materially. Do not send an update for every tool call or Web Search.
- A visible progress update contains only the product name, an indicative completion percentage, elapsed time, and approximate time remaining. Use Azerbaijani and this compact pattern: `Məhsul məlumatları hazırlanır — təxminən 60% · keçən vaxt: 3 dəq · qalan vaxt: ~2 dəq`.
- Percentages and time remaining are estimates, not promises. Derive them conservatively from completed work and elapsed time; never expose the internal phase used to estimate them. If there is not enough information for a meaningful estimate, say `qalan vaxt hesablanır` instead of inventing a duration.
- Do not repeat Task ID, source counters, missing-field lists, or technical caveats in progress messages. Task ID belongs only in the completed result summary or a genuine terminal failure.
- The final response is customer data, not an execution report. Begin with the completed product summary and render the required PDF, image, parameter table, manuals, and source coverage without describing the hidden workflow that produced them.

Use hosted, built-in Codex **Web Search** for research. An actual `web_search` event must appear after each search starts. Never substitute model memory, shell/network commands, browser automation, MCP search, OpenRouter, Exa, Firecrawl, Azure, or the application's paid search pipeline. New plugin searches are submitted anonymously to the Kontakt web platform through its limited submission endpoint, with local backups and locally generated PDFs; the plugin has no direct database credentials or access. Existing local-only searches are not uploaded. The read-only `inspect_product_image` tool may retrieve an image URL discovered through Web Search solely to return its actual pixels for visual inspection; it is not a search provider.

For new searches, completion requires `platformStored: true` from the save response as well as the PDF and full result. If platform submission fails, keep the same task ID and retry the save; do not start duplicate searches or claim web storage succeeded. If the service remains unavailable, explain in Azerbaijani that the local result was retained but web saving was not confirmed. Do not expose the private per-search submission capability. PDFs remain on the user's device; the web record stores parameters, sources, evidence and product image links, not local file paths or chat history.

## Start and research

1. This workflow is supplied by `prepare_product_search` before each new product request. Keep its `runtime_id` through variant choices, schema lookup, image inspection, and task creation. Pass that ID to tools before a task ID exists; subsequent task operations use their saved version automatically. Call `parameter_connection_status` when local storage status is unknown. Never ask the customer to sign in, register, provide a password, or wait for account approval. Continue the original product request in the same turn. If local storage cannot be prepared, explain the failure briefly in Azerbaijani.
2. Use the exact submitted product identity. Supported categories are `phone`, `tablet`, `notebook`, `fridge`, and `washing_machine`.
3. Resolve product variants before calling `start_product_search`. Azerbaijan is the fixed target market, not a variant question. First establish which configurations of the exact product are available in Azerbaijan using applicable official manufacturer/support evidence and exact model-code mappings. Search globally for evidence, but restrict every offered option to configurations verified for Azerbaijan. A worldwide variant list or a label such as "international" does not establish local availability. A retailer's partial stock list is not the complete variant set; preserve the source restrictions below. Ask only when a specification dimension is missing, invalid, or incompatible and more than one verified Azerbaijan-market value remains compatible with the user's choices; when exactly one applicable value is verified, apply it without asking.
    - Do not ask the user to choose a country or a worldwide regional edition. SIM configuration, keyboard layout, energy-label edition and other region-dependent specifications may still require a choice, but only between configurations independently verified as available in Azerbaijan. Ask about the unresolved specification, not an unrestricted "international / eSIM-only / China" menu.
    - Lack of Azerbaijan-market evidence is an evidence gap, not proof of multiple local variants or proof that the user's configuration is invalid. Continue targeted research; if applicability remains unverified, disclose that limitation and leave affected specifications unresolved rather than inventing choices, defaulting to an international model, or claiming local availability. Do not substitute a different product.
    - Ask one dimension at a time. Never combine colour, storage, memory, capacity, connectivity, or another variant dimension in one choice card.
    - Resolve colour first whenever colour is missing or the submitted colour is not offered for the exact model. If the submitted colour is invalid, say so briefly in Azerbaijani and list every verified colour for that model. Do not omit less common colours and do not switch to a related model merely because it has the requested colour.
    - After the customer chooses colour, recalculate compatible configurations and resolve storage or its category equivalent second: internal storage for phones and tablets; SSD/internal storage for notebooks; capacity/size for refrigerators; washing load capacity for washing machines. If the submitted value is missing, invalid, or incompatible with the selected colour, list every compatible verified value.
    - Then resolve every other configuration dimension that still has multiple verified compatible choices within Azerbaijan, one at a time. For phones and tablets this may include RAM, Wi-Fi/cellular connectivity or SIM configuration. For notebooks this may include RAM, processor, graphics, operating system, display or keyboard layout. For refrigerators this may include finish, door/layout, installation type, capacity class, dimensions or applicable energy-label edition. For washing machines this may include drying capability, spin speed, installation type or dimensions. Apply the same Azerbaijan-market restriction and sequential rule to any new category-specific variant dimension supported later.
    - Recompute the valid option set after every answer. Show only combinations verified for Azerbaijan and compatible with all earlier selections, but show the full verified set for the current dimension. This restriction also applies to the colour and storage choices above. Never invent a Cartesian combination from independently listed colours and capacities.
    - Use the native choice UI and keep the turn active while waiting. In Plan mode, use synchronous `request_user_input` when available. In Default mode, use `request_user_input_async`. A UI-preselected value or acknowledgement is not the customer's answer. If the native UI limits how many buttons it can display, put the complete verified option list in the Azerbaijani question text and accept the customer's exact selection; never present a truncated subset as the full list.
    - Do not use a Markdown bullet list when the native choice UI can show the complete set. If no interruptible choice UI is available, ask one concise Azerbaijani plain-text question containing the full list and end the turn waiting for that single answer. Do not ask the next dimension until the current one is answered.
    - Keep the pending choice active for up to five minutes when an interruptible wait is available. Do not use `:codex-followup`. Do not start or save research until every ambiguous variant dimension is resolved. Never silently substitute a related product.
4. An explicit user request to search for a product authorizes `start_product_search` and the final `save_product_search_result`; run both without asking for a second confirmation. Ask for approval immediately before `rerun_product_search` or `cancel_product_search`. Native research uses normal Codex usage and does not consume OpenRouter, Exa, Firecrawl, or Azure balance.
5. Call `start_product_search` and use its exact ordered schema and per-field Kontakt normalization and image-analysis contracts.
6. Invoke native Codex Web Search and research naturally. Choose queries, languages, websites, result types, and query count according to the evidence found. Do not impose fixed modes, a fixed stage sequence, a search budget, a source-count quota, a country limit, a general domain allowlist, or a fixed coverage threshold.
7. Apply exactly one website exclusion: never select, open for evidence, cite, or save an Azerbaijani retailer website. Azerbaijani official manufacturer sites are allowed. International retailers, news pages, specialist sites, regulatory records, manuals, databases, catalogues, forums, and other relevant sources may be used when they provide useful exact-product evidence.
8. Prefer sources in this order when they are applicable to the exact product: official manufacturer product/specification page; official support page, manual, datasheet, label, or regulatory document; then reliable nonofficial sources. Official sources have priority, but do not stop discovery merely because one official page was found.
9. Search results and snippets are discovery clues only. Open and read every page used in `sources`, `source_url`, or `supporting_sources`. Record its direct URL in `openedSourceUrls`. Never quote a snippet as field evidence.
10. Match the exact model, model code, generation, edition, capacity, and configuration. Target the Azerbaijan-market configuration for regional values, but search globally and use any relevant website. A foreign official country page proves only that country's configuration unless evidence establishes applicability to Azerbaijan.
11. Extract every schema field supported by the opened evidence, normalize it to the returned Kontakt contract, and calculate missing and conflicting fields. Before declaring a conflict, verify that the claims describe the same metric, unit, standard, time period, product configuration, and market. Different definitions are separate facts, not competing values.
12. For every missing field, continue researching naturally. Use the exact field name, synonyms, manufacturer terminology, model codes, useful languages, manuals, PDFs, labels, regulatory records, component documents, images, and any new source type likely to resolve it. After discovery or grouped searches, run at least two dedicated Web Search queries for each still-missing field using materially different formulations, and record each query with a `fields` array containing only that field. A broad query cannot count as dedicated recovery for multiple missing fields. This is a minimum safeguard, not a search limit. Do not announce that the draft is ready, that unresolved fields will be left unconfirmed, or that validation is next until every remaining field has completed this recovery.
13. For every conflicting field, search further until either an applicable official source resolves the conflict or a clear independent majority can be established. Before leaving a conflict unresolved, reopen every already-discovered applicable official page and document its exact statement in `officialSourceReviews`; do not assume another search is needed when an opened page already contains the answer. Match the full variant name and model code: a base model must never overrule a `Pro`, `Pro+`, edition, generation, storage, or regional variant. If one applicable exact-variant official value remains after that review, select it with `official_priority`; `unresolved` is allowed only when applicable exact-variant official sources still disagree or none provides the value. A claimed majority requires at least three independent evidence URLs and more support for the selected value than for alternatives. Copied feeds, mirrors, and sites repeating one source count as one evidence chain. Check each source for internal contradictions and template contamination; a page that contradicts its own product layout or identity must be down-ranked and cannot overrule coherent exact-model evidence. Preserve the conflict and leave it unresolved when there is a tie, an applicable official contradiction, or no clear majority. Record `conflictingFields` and `conflictResolutions`.
14. Run native Codex image analysis for every supported category. Use official exact-product images first, followed by images from other opened allowed sources. Inspect the actual pixels; filenames, alt text, and snippets are not visual evidence.
15. Follow each field's `imageAnalysis.mode`:
    - `direct_product_photo`: a clear exact-product photo may support the field when the required area is completely visible.
    - `readable_exact_model_label_only`: never infer the value from appearance. Accept it only when an exact-model label, manual page, specification graphic, rating plate, packaging panel, or energy label visibly prints it.
16. Every image-derived value requires `evidence_kind`, `image_url`, `visible_detail`, `visual_confidence`, and exact-product identity. Use at least 0.88 visual confidence. For a negative visual value such as no display, no ice maker, no freshness compartment, or no remaining-time indicator, set `complete_relevant_area_visible: true`; otherwise omit it. Verified direct visual evidence has priority for direct-photo fields, and any conflicting text must remain documented.
17. Analyze or explicitly mark unavailable every `directProductPhotoFields` entry returned by the category schema. A real native image search/analysis attempt is mandatory even when no usable image is ultimately found. Open each image URL and inspect its actual pixels. Record an `observations` entry for every inspected URL with its source page, exact-product verification, whether it is usable, the fields visibly shown, and a concrete visual observation. Record field-specific `unavailableReasons`; a generic reason for all fields is invalid. Do not list an image URL as inspected when only its filename, thumbnail metadata, alt text, or search snippet was seen. Do not mark a visible field unavailable when a usable exact-product image shows it. Every accepted image field must have full image field evidence, and accepted and unavailable field lists must not overlap.
    - For a refrigerator field that remains blank because the inspected view does not expose it, make a dedicated exact-model image-view Web Search for that field before marking it unavailable. Seek the missing view—for example an open refrigerator interior, open freezer, complete exterior, or controls—not another copy of the same front photo. Inspect any credible exact-variant image pixels found. Record the actual query in `targetedSearches` with only that field in `fields` and `stage: image_view_recovery`. If no applicable view is found, keep the field unresolved; do not infer hidden or absent features from an incomplete photo. This search is in addition to the two dedicated missing-field queries.
18. Stop when all fields are evidence-backed or when varied additional research for every remaining missing or conflicting field produces no credible new evidence. Every unresolved field must have at least two documented, dedicated, materially different targeted searches. Use `—` and `unresolved` instead of guessing.
19. Every non-empty value needs field evidence. Preserve source URL, source type, exact-model match, a concise opened-page excerpt or visible image observation, confidence, and all independent supporting sources.
20. Before presenting a parameter table or saving, set `nativeWebSearchUsed: true`, record the real `nativeWebSearchEventCount`, set `sourcePagesOpened: true`, and include complete `openedSourceUrls`, `imageAnalysis`, `targetedSearches`, `conflictingFields`, and `conflictResolutions` data.
21. Call the read-only `validate_product_search_draft` tool with the complete proposed result. It does not require approval and does not write data. Treat every validation failure as an internal, recoverable step: never end the turn, never tell the user that image-evidence metadata or Kontakt validation rejected the result, and never present the incomplete draft as the result. Correct metadata aliases and report structure, perform every additional field-specific search requested by validation, then retry until validation succeeds. Canonical image observation keys are `exact_product_page_verified` and `visible_fields`; canonical conflict keys are `outcome`, `evidenceUrls`, `officialSourceReviews`, and `reason`. The tool also accepts common aliases and normalizes them, but output canonical keys on every retry. Use the validator's `normalizedParameters`, `filled`, and `completenessPct` when the user asks to preview before saving.
22. Before validation, choose at least one clear exact-product image whose pixels were successfully retrieved and inspected with `inspect_product_image`. A filename, search thumbnail, metadata-only result, failed retrieval, unsupported format, access-denied response, generic image icon, broken-image placeholder, transparent/blank canvas, hotlink-block notice, or unrelated promotional graphic is not an acceptable product image. The presentation image must use a stable public direct HTTPS image URL that loads without authentication, cookies, request headers, expiring signatures, or a referring page. Prefer a manufacturer-hosted static image. Avoid `blob:`, `data:`, page URLs, redirect wrappers, temporary CDN tokens, and URLs whose successful display depends on a retailer session. When the primary host may block embedding, inspect a second exact-product image from a different hostname and use the stable candidate; never knowingly render a broken placeholder. Pass accepted images in `product_images` with their direct image URL, opened source-page URL, title, and verified exact-model match. After draft validation succeeds, call `save_product_search_result` once without another confirmation. Its response includes the saved app-format result and automatically generated standard PDF. If the result is absent, fetch the task with `get_product_search` using `view: app`. If `pdfReport.generated` is not `true`, call `generate_product_search_pdf` for the saved task before finishing. In the same response that reports completion, always link the generated PDF and always render the complete saved parameter table. Never end a successful search with only a status, task ID, percentage, source list, or an offer to show the table or PDF later.
23. When `wait_product_search` or another status check first reports `done`, immediately call `get_product_search` with `view: app`. If no generated PDF is returned, call `generate_product_search_pdf`, then render the PDF link and complete table without waiting for the user to request them.

Do not use `wait_product_search` while conducting research in the same Codex task. It is intended for monitoring work performed by another task or client.

## Refrigerator evidence semantics

- Before applying household refrigerator fields, identify the appliance subtype. A commercial bottle/display cooler is not automatically a one- or two-chamber household refrigerator. Preserve an exact supported catalogue type such as `Butulka soyuducusu`; do not force `İkikameralı` from two glass doors or confuse the door count with chamber count.
- Commercial climate classes can be numeric (`4`, `4+`) or display-cabinet classes (`CC2`). These are different classification systems. Keep the exact evidenced class and its system; do not convert one into the other or drop it because it is not `SN/N/ST/T`.
- For a commercial cooler, search the exact model's current official product page, technical sheet, manual, energy/product-information label, and archived catalogue. Check full suffixes and refrigerant/energy-label generation before transferring capacities, dimensions, noise, or climate values between documents.
- For market-sensitive dimensions, capacities, noise, climate and energy values, verify that the source's version applies to Azerbaijan. A Turkish, Russian, or other country page does not outrank an applicable Azerbaijan-market document merely because it is official. If applicability cannot be established, keep the disputed field unresolved and explain the market/version distinction outside the parameter table.
- Before saving, reconcile every high- or medium-confidence source excerpt against the normalized table. If a quote explicitly supports a field but normalization leaves `—`, correct the normalization or downgrade and document the genuine conflict; never save it as a verified blank. Recheck the final brand spelling in both the table and generated PDF.
- Treat `Toplam faydalı həcm` as total net/usable capacity and `Toplam həcm` as gross/nominal total capacity. A page reporting 531 lt usable and another reporting 544 lt gross may describe the same appliance; map them to separate fields instead of creating a conflict.
- Apply the same distinction to usable refrigerator/freezer compartment capacities versus gross compartment capacities. Do not put a gross compartment value into a field whose schema meaning says usable/net.
- When energy classes differ, identify the labeling system and market first. Old `A+`/`A++`/`A+++` labels and newer `A`-to-`G` labels are not automatically contradictory. Save the class applicable to the Azerbaijan-market configuration and document the other standard.
- A one-unit noise difference may be rounding, a label revision, or a regional configuration. Inspect labels/manuals and independent exact-model sources before choosing it; do not average values.
- For Side-by-Side refrigerators, verify freezer position from a complete open-interior image or exact documentation. Reject internally inconsistent catalogue claims such as a Side-by-Side layout paired with a bottom-freezer template value.
- Product photos can directly resolve visible refrigerator fields such as shelf material, handle type, door layout, display presence, and freezer position when the required area is fully visible.
- A closed-door catalogue hero image is insufficient for shelves, freshness drawers, freezer contents, chamber count, or absence of an ice maker. Check exact-model galleries and open-door views before declaring these fields visually unavailable. Preserve the exact model suffix and regional variant when assessing whether another view applies.

## Kontakt formatting

Follow every field's normalization contract exactly. Examples include `Var`/`Yox`, `128 GB`, `5000 mAh`, `170 qr`, `1.62 kq`, `188.4 sm`, `35 dB`, `288 lt`, `1400 dövr/dəq`, `SN, N, ST, T`, and dimensions with ` × `. `SIM-kart sayı` is `1` or `2`, never `1 fiziki SIM`. A negative boolean is `Yox`, never `Yox¹`. For phones, `Video formatı` is the single highest quality such as `4K`; `Video icazəsi və kadr tezliyi` is the highest quality plus range such as `4K, 24-240 kadr/s`; and `Şəbəkə standartı` is the highest generation such as `5G`. For foldable phones, `Ekran` must contain both diagonals in Kontakt order—main/internal first, cover/external second—formatted as `6.7" / 3.4"`; never keep only one display when both are evidenced.

## Present results

Render every successful search automatically in this order: product name; one compact line with category, confirmed/total parameters and date; generated Kontakt PDF link labeled `PDF-i yüklə`; one accepted exact-product image; complete numbered parameter table; a short unresolved-data note if needed; manuals when present; linked source-coverage table. Use the standard `kontakt-product-report-v2` PDF with the saved image, every saved value, and clickable per-parameter source links. Never recreate the PDF ad hoc or modify saved values. The result is incomplete until the PDF link, real product image and complete parameter table are visible. Replace a failed image with another inspected exact-product image; never leave a broken placeholder. Do not ask whether the customer wants the table or PDF.

The parameter table columns are `№`, `Parametr`, `Dəyər`, and `Mənbə`. Use the saved `parameterRows` in schema order. Show every field and `—` for unresolved values. Copy every value cell verbatim from `displayParams` or `displayParamsRU`: render `Yox` exactly as `Yox`, never `Yox — Wi-Fi versiyası`. Value cells contain only normalized values—never citations, footnote numbers, links, or evidence markers. They also never contain parenthetical explanations or explanatory suffixes. Put clickable proof website names in the separate `Mənbə` cell beside each confirmed value, using that row's exact supporting page URLs, for example `[teka.com](https://www.teka.com/...)`. Do not replace them with homepage links or attach a source that does not support that parameter and value. Include the row's supporting websites without duplicates. Unresolved rows show `—` in the source cell. For an older confirmed row with no saved evidence link, show `Mənbə göstərilməyib`; never invent one. Put necessary caveats outside the table.

Copy the returned `parameterTableMarkdown` directly when available; it already has the correct Azerbaijani headings, saved values and per-row proof links. Do not rebuild its source assignments from memory.

The source-coverage table is mandatory and has `Mənbə`, `Tapılan parametrlər`, and `Ümumi parametrlər` columns. Link each source name to its direct URL and show `supportedFieldCount / requiredFieldCount` for every opened website saved as a source, including sources that contributed zero accepted fields. Use the saved `sourceCoverage` or `sources` data; do not estimate counts from prose.

Keep the opening summary to two lines: the product name and `Soyuducu · 27/29 parametr təsdiqlənib · 23.09.2026` (using the actual category, counts and date). Avoid technical status messages and task IDs in the opening; include a task reference only if requested. Use short website labels and put official sources first in the source summary. Explain `—` once below the table as `Məlumat təsdiqlənməyib` rather than repeating warnings on every row.

State public-service access, native-web availability, deadline, save, and cancellation failures clearly. Do not describe them as missing product data.
